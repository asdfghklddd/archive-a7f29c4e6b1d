工作主线

iOS 与 AI 实时链路

iOS 仓库的 PR 1 把旧 WebSocketManager 替换为 ChatSSEClient、UserEventsSSEClient 和独立 SSEParser，接入 /ios/api/chat 与 /ios/api/events，同时调整登录超时、上传结果和消息解码。该 PR 涉及 38 个文件，新增 800 行、删除 1178 行，并加入 SSE、视觉结果和请求契约测试。构建和单元测试通过，UI test runner 在模拟器启动阶段失败，因此不能把 UI 测试写成成功。

后端同期经历了明显的拆分过程。PR 11 把 Gemini、聊天和异步上传混在 34 个文件中，评审发现消息截断可能破坏 tool call 与 tool result 配对，内存中的 job status 也缺少可靠清理。你主动关闭了该 PR，并写明改用更小的模块化 PR。随后 PR 13、PR 15、PR 16 分别处理完整 turn 截断、带 TTL 与容量上限的异步任务状态、SSE 首帧与早期 abort。三项都通过 CI 和评审。

PR 23 继续把视觉上传做成可观测、可恢复的异步链路。评审曾指出一次普通产品扫描可能清空用户全部库存，外键失败还会留下部分删除状态。修复后，只有显式 replace_existing=true 的 onboarding 重扫才会清理，而且清理发生在确认识别到商品之后。数据库通过单个 PL/pgSQL RPC 原子处理，先解除 routine 引用，只删除 source='scan' 的库存，并限制函数权限。复审确认 40 个相关测试通过，完整套件达到 958 个通过、5 个跳过。

微信小程序质量、安全与弱网

后端领域模型与产品事实来源

商品目录工作包含一次很有价值的错误。PR 47 在共享后端加入 PRODUCT_CATALOG_SCOPE 和 RéVive 品牌过滤，并被小程序工作流越权合并。后端评审指出，两套部署通过各自 Supabase 数据源隔离商品目录，共享代码中的品牌特判会形成重复约束，且难以覆盖所有入口。

遇到的主要问题

范围过大导致评审困难

早期后端 PR 10、PR 11 和 PR 12 都是大范围同步。PR 10 因重复类型声明无法构建，PR 11 收到两个阻塞问题，PR 12 达到 75 个文件。之后你把同一批工作拆成 2 到 5 个文件的 feature PR，评审和验证明显更聚焦。后端 42 个 PR 中有 25 个收到外部评审，9 个经历 changes requested，22 个最终获得 approval。

分支纪律仍有不一致

后端大多使用一项工作对应一个分支。商品目录还采用了清楚的三层 stacked PR。前端的 feat/miniapp-andy 被重复用于 4 个 PR，曾产生 335 个文件和 261 个文件的超大集成 diff。2026 年 8 月抽查的 8 个默认分支 commit 没有 GitHub PR 关联，其中 conversation-first 后端改动在当天被 revert。面试时不必回避，可以说明自己后来更重视短生命周期分支、明确 base、按依赖顺序合并和禁止未经授权直推共享 main。

合并、部署与客户端可用并不等价

当前仍有 5 个开放 PR，包括后端 PR 84、PR 95、PR 105、PR 106，以及前端 PR 17。其中 care guide 的 PR 103 虽已合并，PR 说明也明确写着 MiniApp 必须改为 POST 新模板才会命中该路由，后续 v2 契约仍在 PR 106 中。面试时应说合并和 CI 通过，不要把这些状态扩大成已经部署或已经被用户使用。

S 情境

iOS 客户端还依赖旧 WebSocket，而当前后端已经采用 HTTP POST 加 SSE。聊天首帧、用户事件、图片上传结果和 abort 的契约不一致。最初的后端同步 PR 范围太大，评审又发现上下文截断会破坏工具调用配对，异步任务状态可能长期留在内存。

T 任务

把 iOS 与后端实时链路对齐，同时保证长对话、早期取消和异步视觉任务在失败场景下仍有清楚状态，并把改动拆成可评审单元。

A 行动

在 iOS 中新增聊天 SSE、用户事件 SSE 和独立 parser，使用 AsyncThrowingStream 处理流式响应，补上非 2xx、token、abort 和视觉事件测试。后端关闭混合范围 PR，把问题拆成完整 turn 截断、带 TTL 与容量上限的 job status、可取消的早期 turn_start。视觉上传又加入阶段耗时、显式替换参数和原子数据库清理。针对 review 指出的全量库存误删，默认扫描保持 additive，空识别不会触发清理，RPC 只删除 scan 来源的数据并先处理外键。

R 结果

iOS PR 1 与后端 PR 13、15、16、23 均合并。iOS 构建和单元测试通过。后端 PR 16 在修复早期 abort 后完成 804 个测试，PR 23 的相关测试 40 个全过，完整套件 958 个通过、5 个跳过。结果只证明代码合并和验证完成，不能声称生产指标改善。

九十秒口述稿适合第一轮完整回答

我负责过一次 iOS 与 AI 后端实时链路的对齐。iOS 当时还在使用 WebSocket，后端已经切到 HTTP POST 加 SSE，聊天、用户事件和异步图片任务的状态不一致。我先在 Swift 端拆出聊天 SSE、用户事件 SSE 和 parser，用异步流统一处理数据与取消。后端第一版改动过于集中，review 指出两个真实风险，长对话可能截断在 tool call 中间，job status 也可能一直占内存。我关闭了混合 PR，拆成几个独立分支，分别按完整 turn 截断、给任务状态加 TTL 和容量上限、让首帧之后立即可 abort。后来视觉上传 review 又发现普通扫描可能误删全部库存，我把替换改成显式参数，并用一个受权限保护的数据库函数原子清理 scan 来源数据。相关 PR 最终都合并，关键测试从 40 个专项用例到 958 个完整套件都通过。这件事让我形成了一个习惯，实时系统要同时设计成功路径、取消路径和持久化边界。

FOLLOW-UP DEFENSE

面试追问

10 questions

主要证据来自 iOS PR 1、后端 PR 11、PR 13、PR 15、PR 16 和 PR 23。

01追问一 你具体是如何解决的

建议回答

我先按协议和生命周期拆问题。聊天是一次 POST 对应一条 SSE 响应流，用户事件是应用级的长期 GET 流，视觉上传又是创建 job 后轮询状态。我在 iOS 里把这三种生命周期分开，新增聊天 SSE client、用户事件 SSE client 和独立 parser，用 AsyncThrowingStream 处理聊天结果和取消。后端则把原来混在一个 PR 里的问题拆开，分别处理完整 turn 截断、job status 清理、首帧和早期 abort。视觉扫描涉及删除时，我又把替换动作改成显式 replace_existing，空识别先返回，真正清理通过单个数据库函数原子执行。

如果面试官继续问代码位置，可以补充

  • iOS 使用 ChatSSEClient、UserEventsSSEClient、SSEParser 和 ChatViewModel。
  • 聊天请求走 /ios/api/chat，长期事件走 /ios/api/events，取消走 /api/chat/abort。
  • 产品扫描默认只增量写入。只有 onboarding 明确要求替换时才调用清理函数。
02追问二 为什么选择 SSE，不继续使用 WebSocket

建议回答

这个选择来自服务端已有契约。用户发送一条消息后，服务端按顺序返回 turn_start、文本增量、工具状态和 turn_end，单个请求天然是一条单向响应流。SSE 可以继续使用普通 HTTP 鉴权、状态码、代理和超时行为，客户端也容易把一次聊天与一次取消绑定。应用级后台事件仍然使用独立的 SSE 连接。WebSocket 适合高频双向通信，但这个场景的客户端上行只有一次请求，所以继续保留 WebSocket 会让两套协议长期并存。

追问如果变成 SSE 是否总比 WebSocket 好，可以回答

没有通用优劣。若产品需要双方持续高频发送、低延迟协作或二进制消息，我会重新评估 WebSocket。这里选择 SSE 是为了匹配现有服务端行为并减少协议分叉。

03追问三 为什么要把聊天流和用户事件流分开

建议回答

两者的生命周期不同。聊天流属于一条用户请求，可以结束、失败和 abort。用户事件流跟随登录会话，用来接收视觉任务完成等后台事件。如果共用一个连接，一条聊天的取消或错误可能影响后台事件，重连策略也会混在一起。分开以后，两边可以独立鉴权、取消和恢复，状态机更容易测试。

04追问四 什么叫按完整 turn 截断上下文

建议回答

Agent 历史里一轮对话可能包含用户消息、assistant 发起的 tool call、tool result 和最终回答。如果直接取最后 N 条 message，切点可能落在 tool result 前面，模型会看到孤立结果，或者看到一个没有结果的 tool call。我的处理方向是先识别完整用户轮次，只在轮次边界截断，让工具调用保持配对。长期方案还可以按 token 预算选择完整轮次，但边界约束仍要保留。

05追问五 为什么 job status 需要 TTL 和容量上限

建议回答

job status 当时保存在进程内存。如果只在客户端查询时清理，已经通过 SSE 收到结果或者从不轮询的任务就可能一直留下。TTL 解决过期问题，容量上限避免异常流量持续占用内存。这个方案适合当时的单进程状态查询，但它不能解决多实例共享和进程重启。规模扩大后，我会把 job 状态放进持久化存储，并继续保留过期策略。

06追问六 为什么 replace_existing 要显式传入

建议回答

普通产品扫描通常应该追加或更新商品，只有 onboarding 重扫才有替换语义。默认清空会把一个少量商品照片解释成用户要重建全部库存，失败代价很高。显式参数让破坏性动作只能由明确场景触发。代码还把清理放在识别出商品之后，所以模糊照片不会造成先删后空。

07追问七 为什么用数据库函数原子清理

建议回答

原方案连续执行多条 delete。中间一条因为外键失败时，前面的删除已经生效，会留下部分状态。单个 PL/pgSQL 函数在一个事务里先解除 routine 对 scan 库存的引用，再删除 compatibility、recommendation 和 scan 来源库存。任一步失败都会一起回滚。函数还固定 search_path，撤销 public 和 anon 执行权，只允许 authenticated 与 service role，减少越权调用。

08追问八 你为什么觉得这个方案更好

建议回答

我判断方案好坏看三个条件。协议是否与真实生命周期一致，失败时能否回到确定状态，破坏性操作是否默认安全。分离两类 SSE 让生命周期清楚，完整 turn 和早期 abort 保证状态一致，显式替换与事务清理限制了数据损失范围。这些判断都有对应测试，不依赖一句代码更优雅。

09追问九 你如何证明修复有效

建议回答

我用了分层验证。iOS 有 parser、请求契约和视觉事件单元测试，工程构建和单元测试通过。后端对完整 turn、早期 abort、普通扫描不清理、空识别不清理、显式替换和 RPC 调用都做了回归测试。PR 16 修复后完整套件有 804 个测试通过，PR 23 的相关测试 40 个全过，完整套件有 958 个通过、5 个跳过。UI test runner 当时未能在模拟器启动，所以我不会把 UI 测试算作成功。

10追问十 如果现在重做，你还会改什么

建议回答

我会给上传增加 idempotency key，避免客户端重试创建重复 job。job 状态会从单进程内存迁到可持久化的共享存储，便于多实例和重启恢复。客户端还应记录首包时间、断流阶段、abort 是否生效和任务最终状态，用真实数据决定超时与重试参数。

S 情境

一次小程序全量前端审查修复了冷启动深链等六类问题。复查时发现 product 页直接展示 URL 参数中的品牌、商品名、推荐理由和购买链接。新加入的深链与转发能力使伪造卡片更容易传播。小程序同时存在多处弱网静默失败，用户会看到回复消失、分析中断或错误归因到照片质量。

T 任务

及时封住由自己前一项改动放大的攻击面，并在不依赖后端新接口的前提下，让聊天、鉴权和视觉轮询在微信网络环境中给出可理解、可恢复的结果。

A 行动

面试追问

11 questions

主要证据来自 前端 PR 16、PR 18、PR 19 和 PR 20。

01追问一 你是怎么发现这个安全问题的

建议回答

我沿着新加的冷启动深链从入口追到最终消费点。product 页没有按 id 向后端取商品，它直接把 URL 参数中的品牌、商品名、推荐理由、图片和购买链接渲染出来，购买链接还能进入剪贴板。前一个 PR 又允许该页面冷启动直达，并把收到的参数继续用于分享。我进一步检查了后端接口，当时没有可用的商品详情查询，所以前端无法验证这些文本是否属于真实商品。

02追问二 为什么不只过滤恶意 URL

建议回答

只限制 javascript: 或 HTTP 只能保护链接协议，无法证明品牌、商品名和推荐理由是真的。攻击者完全可以使用一个 HTTPS 钓鱼站，同时伪造一张 PHASE 风格的知名商品卡。由于当时没有后端详情接口，最稳妥的止血是暂时移除 product 冷启动深链和转发。落地页的 HTTPS 校验仍然保留，用来保护站内导航和未来新增入口。

03追问三 移除功能会不会影响用户体验

建议回答

会，代价是 product 页暂时失去分享和扫码直达。我在 PR 里明确写了这个取舍和恢复条件。后端提供按稳定 product id 查询详情后，前端可以只从 URL 接收 id，正文和购买信息都从权威接口加载，再恢复深链与分享。在可信数据源缺失时，我选择缩小入口，因为错误的商品和购买链接会直接影响用户决策。

04追问四 你为什么还要在落地页再校验一次

建议回答

原来的 HTTPS 检查只存在于一个构造导航参数的位置。新的入口、二维码或者未来代码可以绕过它。安全约束应放在数据真正被使用的位置，所以落地页复制链接和显示图片前还要复查协议。入口限制和消费端校验覆盖的是不同失效方式。

05追问五 弱网问题具体怎样修

建议回答

我把一次聊天和视觉任务按失败阶段拆开。SSE 收到非 2xx 时显式生成 error event，401 走统一登出。网络层 fail 和首包超时也转成用户能看懂的错误。流在 turn_end 前中断时，已经收到的文本保留下来并标注中断。视觉 job 已经创建以后，瞬时轮询失败允许恢复，成功一次就清零错误计数。401、403、404 没有重试价值，所以立即失败。

06追问六 为什么只重试轮询，不重试上传

建议回答

/api/upload 当时没有幂等保证。重新上传可能创建第二个 job、重复分析并消耗额度。轮询只是查询已存在 job 的状态，短暂失败后重试不会改变业务数据。因此我把重试放在读取状态这一层，并把身份、权限和 job 不存在这类确定错误排除在重试之外。

07追问七 为什么设置连续三次失败才结束

建议回答

代码允许前两次瞬时失败，第三次连续失败才结束，一次成功就重置计数。这个值是在可恢复性和等待时间之间做的保守选择，当时没有线上网络分布数据支撑更精确的参数。我不会把它描述成经过统计证明的最优值。后续应通过轮询失败次数、恢复比例和总等待时间来调整。

08追问八 为什么把 catalog tool result 当成商品卡事实来源

建议回答

旧逻辑要求 LLM 正文精确包含 catalog 商品名才能渲染卡片。自然语言可能使用简称、翻译或不同标点，工具已经找到真实商品，卡片却可能消失。tool result 是后端查询并校验过的结构化数据，更适合提供图片、价格和购买链接。LLM 继续负责解释推荐理由，商品事实由 catalog 提供。前端还限制最多三个候选并去重，避免把整页搜索结果都当成推荐。

09追问九 你如何验证弱网修复真的覆盖了问题

建议回答

PR 19 新增 19 个用例。我逐项撤销修复后，其中 13 个会失败，说明这些测试能区分修复前后的行为。剩余 6 个是对照用例，用来保证 2xx、空回合和不可重试状态没有被误伤。最终 129 个测试文件、706 个测试、TypeScript 检查和生产 API 构建通过。

10追问十 这是你自己引入的问题，你怎么向团队解释

建议回答

我会直接说明前一个 PR 增加了 product 深链和转发，使已有的 URL 信任问题更容易被利用。我在修复 PR 里写清攻击路径、影响和恢复条件，没有把问题包装成无关的历史遗留。发现后先缩小入口，再补消费端测试。对我来说，承担责任包含把因果写清、快速恢复安全状态，并让同类问题以后更容易被发现。

11追问十一 如果现在继续完善，你会做什么

建议回答

我会让 product 页面只接受稳定 id，由后端返回经过权限和目录校验的详情。购买链接应由服务端生成或映射，并记录打开失败与复制行为。网络方面会增加错误码、首包延迟、断流阶段和轮询恢复率，随后用数据调整超时和重试。上传接口也应加入幂等键。

11 questions

主要证据来自 后端 PR 47、PR 48、PR 49、PR 50 和 PR 51。

01追问一 你最初的方案为什么错了

建议回答

我把小程序只展示 RéVive 的要求理解成共享业务代码需要品牌过滤。团队实际采用两套 Supabase 数据源，小程序环境只导入批准的 RéVive 商品，iOS 环境使用自己的完整目录。代码层 scope 会与数据隔离重复，而且需要在 Agent 工具、HTTP 路由、后台任务、缓存和价格查询等入口重复实现，遗漏一个入口就会出现行为不一致。

02追问二 发现问题后为什么选择立即回滚

建议回答

当时已经确认方案依赖错误的架构前提，而且合并没有得到后端团队授权。继续在错误方案上修补会扩大 diff，也会让共享 main 长时间处于有争议状态。PR 48 精确反向恢复 PR 47 的 12 个文件，没有改生产数据。回滚先恢复已知基线，让新方案能够独立评审。

03追问三 为什么数据源隔离更合适

建议回答

小程序环境的数据库只有获批商品，任何正常查询都会自然落在同一范围内，Agent、HTTP 和后台任务无需各自记住品牌规则。共享代码也能继续服务 iOS 环境。这个方案依赖严格的导入流程和目录审计，所以数据源隔离不能只靠口头约定，需要在导入、Storage 和定期 audit 上持续验证。

04追问四 为什么后来又增加 active catalog 边界

建议回答

数据源决定环境里有哪些商品，active catalog 决定应用怎样引用这些商品。历史代码里仍可能使用模型生成文本、fixture 或旧缓存。新方案要求商品状态保存 canonical catalog id，Agent 的搜索、价格和写入都通过同一目录服务，服务端页面也从该目录取品牌、图片和价格。这样可以避免模型创造商品，也能让不同入口得到一致事实。

05追问五 为什么拆成三个 stacked PR

建议回答

三层存在明确依赖。数据库先提供可空外键，Agent 和 domain tool 才能保存 catalog id，最后 server flow 才能全面切换。若一次提交，reviewer 会同时面对 migration、工具和大量路由，发生问题也难以确定回滚层级。stacked PR 让每一层只展示自己的 diff，并明确先合并 49、再把 50 retarget 到 main、最后处理 51。

06追问六 为什么外键先设计成可空

建议回答

现有数据库有历史库存、routine 和 recommendation，它们未必都能立即映射到 catalog。强制非空会让 migration 或旧数据读取直接失败。可空外键允许 schema 先安全上线，新写入逐步要求 canonical id，无法解析的旧记录可以明确降级或 fail closed。等迁移覆盖率和数据审计达到要求后，再评估是否收紧约束。

07追问七 什么叫 fail closed

建议回答

当 catalog 为空、不可访问或者商品无法匹配时，系统不再回退到模型编造、旧 fixture 或不受控的外部文本来生成购买信息。它可以返回没有可验证商品，或者只保留不带商品事实的建议。代价是短期内可能少展示内容，但不会把未经验证的商品当成真实推荐。

08追问八 你怎样处理和后端团队的协作问题

建议回答

我先在原 PR 留下记录，说明这次合并缺少后端授权，并停止由小程序工作流继续合并后端。新方案把每层依赖、base 和合并顺序写进 PR，让后端团队能够按自己的节奏审核。以后遇到共享后端和部署边界变化，我会先确认代码所有权、数据源和发布人，再进入实现。

09追问九 你如何证明新方案比原方案更好

建议回答

原方案在 12 个入口附近加入品牌 scope，覆盖完整性很难证明。新方案把范围交给环境数据，把商品真实性集中到 active catalog。PR 49 只处理 schema，PR 50 有 8 个聚焦测试文件和 63 个测试，PR 51 覆盖 onboarding、推荐、计划、皮肤诊断、库存和价格比较，并通过完整测试与构建。它还消除了共享代码中的 RéVive 特判。

10追问十 如果未来同一个数据库需要多个品牌或市场怎么办

建议回答

那时单纯依赖独立数据源可能不够。我会在数据模型中增加 tenant、market 或 catalog scope，并通过数据库查询边界、视图或策略统一限制访问。这个维度需要覆盖导入、读写和缓存键，不能继续用散落在业务代码里的品牌字符串判断。选择哪种方式要看部署是否仍然物理隔离，以及同库跨市场查询是不是实际需求。

11追问十一 这次失败最大的收获是什么

建议回答

你在三件事里承担的共同角色是什么

建议回答

我的共同角色是把客户端症状追到协议、状态和数据库边界，再把修复拆成可以验证的 PR。iOS 项目里我处理实时协议与异步任务，小程序里处理可信输入和弱网，商品目录里处理数据源与共享代码的职责。reviewer 提出的阻塞问题也促使我把默认安全、事务性和分支范围纳入设计。

你最擅长的能力是什么

建议回答

我比较擅长跨层排查。一个页面上的思考中消失，我会继续看 SSE 状态码和状态机。一个商品卡显示错误，我会追到 URL、tool result 和 catalog。一个删除失败，我会继续查外键和事务。我的优势来自把用户看到的现象与后端真实状态对应起来，并用测试固定行为。

你最需要提升的地方是什么

建议回答

早期我有把多个问题一起放进大 PR、在架构和所有权没有完全确认时先实现的倾向。PR 11、12 和商品目录回滚都说明这个问题。后来我开始使用短生命周期分支、stacked PR、明确 base 和合并顺序。下一步还需要把这套习惯提前到编码前，通过简短设计说明先确认数据和发布边界。

如果面试官说这些都是 reviewer 帮你修的

建议回答

reviewer 确实指出并在部分 PR 中直接提交了关键修正，我不会抹掉这部分贡献。我的工作包括提出需求和第一版实现、维护 PR、理解阻塞问题、补验证并推动最终合并。更重要的是，我能解释为什么原方案有风险、修正怎样改变了状态和数据边界，以及以后怎样在第一版就避免同类问题。实习中学会使用高质量 review，本身也是我的成长。

如果面试官要求一个量化结果

建议回答

我可以给出代码和验证数字，例如 PR 范围、专项用例和完整测试数。现有材料无法证明线上故障率或转化率变化，所以我不会编一个业务百分比。如果重新做，我会在上线前定义首包时间、断流率、重复 job 数、无效商品卡数和 catalog miss rate，再做发布前后对比。

临场使用方法

  • 每个回答先给判断，再选两个动作，最后给验证。
  • 面试官问为什么时，讲替代方案和代价，不重复实现步骤。
  • 面试官指出失误时，先承认事实，再讲恢复动作和后来怎样改变流程。
  • 被问到生产效果时，明确区分测试、合并、部署和用户指标。
  • 记住关键名词和因果即可，不必逐字背诵整段答案。
