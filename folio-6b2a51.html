01

Swift 类型与数据结构

这一组问题在检查你是否理解 Swift 数据怎样复制、共享和查找。它也是 ARC、SwiftUI 状态和并发安全的入口。

这一章必须会

  • struct 与 enum 是值类型
  • class 是引用类型
  • 值语义不等于一定放在栈上
  • Array、Set、Dictionary 的用途和查找差异
  • SwiftUI 的 View 经常使用 struct

Part A · struct 与 class

两者都能保存属性和方法，差别集中在语义与能力

比较项structclass
语义值类型引用类型
赋值和传参产生独立的值语义多个变量可以引用同一个实例
继承不支持类继承支持继承与运行时类型转换
身份判断通常比较值是否相等可用 === 判断是否同一实例
生命周期不由 ARC 引用计数管理类实例由 ARC 管理
选择建议数据模型、不可变描述、容易推理的状态需要共享身份、继承或引用生命周期的对象
 
struct Profile {
  var name: String
}

var first = Profile(name: "Andy")
var second = first
second.name = "Alex"

// first.name 仍然是 Andy

final class Session {
  var token = "A"
}

let one = Session()
let two = one
two.token = "B"

// one.token 也变成 B，因为两者引用同一实例

Part B · 值类型与引用类型

面试回答要讲复制行为，别把它简化成栈和堆

值类型的关键是值语义。变量得到自己的逻辑值，修改副本不会改变原值。引用类型的变量保存对实例的引用，多个引用可以观察并修改同一个对象。

编译器可以决定具体存储位置，标准库集合还使用写时复制降低复制成本。因此“值类型一定在栈上，引用类型一定在堆上”不够准确。

写时复制

Array、Dictionary 和 String 的副本可以先共享底层存储，某个副本发生修改时再复制。

并发影响

独立的值更容易隔离。共享可变引用需要 actor、锁或其他同步策略保护。

let 的差异

let struct 不能修改其可变属性。let class 引用不能改指向，但实例的 var 属性仍可能改变。

相等与同一

== 表示定义上的值相等，=== 只用于类引用，判断是否同一个实例。

Part C · Array、Set、Dictionary

先看数据关系，再谈性能

类型适合什么数据顺序与重复典型性能
Array有顺序的元素列表，需要按索引访问保留顺序，允许重复按索引通常 O(1)，查找通常 O(n)
Set唯一元素集合，频繁判断是否存在不承诺业务顺序，不允许重复平均查找与插入 O(1)，元素需 Hashable
Dictionary通过唯一 key 查找 valuekey 唯一，业务上不依赖遍历顺序平均查找与更新 O(1)，key 需 Hashable

大 O 表示输入规模增长时的趋势。哈希集合的 O(1) 是平均情况，不能解释成任何输入下都只执行一步。

Part D · SwiftUI 为什么大量使用 struct

View 是界面描述，状态存储由 SwiftUI 管理

SwiftUI 会根据输入和状态重新计算视图描述。轻量的 struct 便于创建和比较。使用 @State 时，实际状态存储由 SwiftUI 管理，View 值被重新创建不等于状态立刻丢失。

struct CounterView: View {
  @State private var count = 0

  var body: some View {
    Button("Count \(count)") {
      count += 1
    }
  }
}

struct CounterButton: View {
  @Binding var count: Int
  // Binding 不拥有状态，只提供读写连接
}

@State 适合视图拥有的短期界面状态。@Binding 让子视图读写其他位置拥有的状态。跨多个视图共享的模型可使用 Observation，并把状态放在需要它的视图共同祖先处。

PHASE 里的真实类型选择

类型和数据结构都对应一个具体关系

  • ChatViewModel 使用可观察的 final class，因为聊天消息、连接状态和进行中的任务需要稳定身份，并由多个界面更新。
  • PhaseImageCache 使用 actor 隔离共享缓存状态，其中 [URL: Task<LoadedImage, Error>] 通过 URL 查找进行中的任务，让相同图片请求共享一次网络加载。
  • LoadedImage 使用 struct 表达一次加载得到的图片与成本。它是传递结果的值，没有共享身份需求。
  • 小程序的图片预加载使用 Map 保存 URL 与本地路径，用 Set 记录需要删除的持久文件，并用队列维持加载顺序。

结合项目的九十秒回答

我会按数据有没有共享身份来选择类型。PHASE 的 SwiftUI View 大多是 struct，它们描述当前界面；聊天 ViewModel 则是 class，因为消息、连接状态和正在运行的 Task 需要稳定身份并持续更新。图片缓存里我用了 actor 管理共享状态，又用 Dictionary 保存 URL 到进行中 Task 的映射。这样收到同一张图片的并发请求时，可以先查 Dictionary 并复用任务。一次图片加载的结果使用 struct，因为它只携带图片和成本，不需要共享身份。这些选择分别利用了值语义、引用身份和哈希查找。
回答顺序 · 业务关系 → 具体类型 → 数据结构 → 产生的效果

继续追问

值类型是不是一定存储在栈上

不能这样保证。值语义描述复制和共享行为，具体存储由编译器和运行时决定。值可能被优化、内联，也可能存在堆分配中。

Array 赋值时会立即复制全部元素吗

标准库集合通常使用写时复制。两个值可以暂时共享底层存储，某个副本修改时才确保得到独立存储。

什么时候会选 Set 而不是 Array

数据要求唯一，并且频繁判断元素是否存在时，Set 更合适。若界面依赖顺序、重复元素或索引访问，Array 更自然。

02

iOS 内存管理

面试官问“你开发时怎样处理内存”，期待听到 ARC、泄漏、资源占用和测量方法。只说 Swift 会自动管理内存不够。

这一章必须会

  • ARC 管理类实例的生命周期
  • 强引用循环会阻止释放
  • weak 与 unowned 不增加强引用计数
  • 图片解码、缓存和 WebView 可能大量占用内存
  • 使用 Memory Graph 与 Instruments 测量

Part A · ARC

ARC 通过强引用判断类实例是否仍被需要

创建类实例以后，每一个强引用都会让实例继续存活。当最后一个强引用消失，ARC 可以释放实例并调用 deinit。ARC 主要管理类实例；struct 和 enum 是值类型，不通过类实例引用计数管理。

01创建实例建立 class 对象
02强引用持有属性、局部变量或闭包引用
03引用关系变化页面退出、任务结束或属性置空
04强引用归零没有对象继续持有实例
05释放资源运行 deinit，回收实例内存

Part B · strong、weak、unowned

引用是否保持对象存活访问形式典型使用
strong会普通引用默认所有权关系
weak不会必须是可选值，对象释放后自动变 nildelegate、可能先释放的回调对象
unowned不会通常非可选，对象释放后继续访问会崩溃生命周期严格依赖且能保证对方更长时

不确定生命周期时，weak 通常更安全。unowned 依赖明确的生命周期保证，不能为了少写可选处理随便使用。

Part C · 循环引用

对象互相强持有，或者对象强持有捕获自己的闭包

final class FeedViewModel {
  var onUpdate: (() -> Void)?

  func bind() {
    onUpdate = { [weak self] in
      guard let self else { return }
      self.refreshVisibleRows()
    }
  }

  deinit {
    // 用于确认页面退出后对象是否真的释放
  }
}

闭包并非一律需要 [weak self]。先判断闭包由谁持有、执行多久、对象是否应该被任务保持。盲目使用 weak 可能让必要工作提前消失。

Part D · iOS 项目常见内存来源

图片和视频

压缩文件大小不等于解码后的内存。4000 × 3000 的 RGBA 图片粗略需要约 48 MB，还可能产生缩放和缓存副本。

无上限缓存

缓存提高复用速度，也可能持续增长。需要数量或总成本上限，并在系统压力或业务边界下释放。

长生命周期任务

Task、Timer、通知、SSE 回调和 Combine 订阅可能继续持有页面或模型。页面离开后应取消不再需要的工作。

WebView 与脚本

网页内容、JavaScript、图片和 WebKit 进程都会占用内存。重复创建 WebView 或页面资源过重需要单独观察。

Part E · 实际排查顺序

用同一条用户路径比较基线、峰值和退出后的回落

  1. 在真机复现进入页面、滚动、加载内容和退出页面。
  2. 查看 Xcode Debug navigator 的 Memory Report，记录当前值和峰值。
  3. 打开 Debug Memory Graph，检查本应释放的 ViewModel、控制器和 WebView 是否仍有引用路径。
  4. 使用 Allocations 查看分配随操作怎样增长，必要时使用 Leaks 查泄漏。
  5. 修复后重复完全相同的路径，确认对象数量和内存曲线能够稳定或回落。

模拟器适合观察对象关系，但不能证明真机内存安全。Apple 明确提醒，模拟器内存仪表保持绿色不代表设备不会因内存压力终止 App。

结合项目的九十秒回答

我在 PHASE 里主要从对象生命周期和资源上限两方面处理内存。长连接方面，我把 SSE 读取放在 Task 里，闭包使用 weak self；用户断开、流结束或对象释放时都会取消任务，避免连接和 ViewModel 被长期持有。图片方面，我做了 PhaseImageCache，给 NSCache 配置 300 项和 24 MB 的成本预算，URLCache 配置 24 MB 内存与 120 MB 磁盘；相同 URL 的并发请求复用一个进行中的 Task，清理缓存时也会取消未完成任务。小程序里我也给富内容、页面数据和图片缓存设置了条目或字节上限，并在账号切换时清空用户态缓存。现有单元测试验证了请求去重、预取限制、淘汰和清理行为。我当时没有形成 Instruments 的前后对比数字，所以我会把这部分说成代码层资源控制，后续再用 Memory Graph 和 Allocations 验证实际内存曲线。
回答顺序 · 生命周期 → 缓存上限 → 并发去重 → 测试 → 测量边界

继续追问

ARC 能不能解决所有内存问题

不能。ARC 可以在强引用归零时释放类实例，但无法自动打破强引用循环，也无法替你限制图片、缓存和 WebView 的资源规模。

weak 和 unowned 怎么选

对象可能先释放，使用 weak 并处理 nil。生命周期严格保证对方始终存在时可以考虑 unowned，但保证失效以后继续访问会崩溃。

内存上涨就是泄漏吗

不一定。缓存、图片解码和系统框架可能保留可复用资源。需要观察对象是否按预期释放、内存是否无限增长，以及在稳定操作后能否达到平台可接受的平衡。

你为什么把图片缓存设成这些上限

这些数值是项目里的资源预算，目的是阻止缓存无限增长，同时保留社区列表的重复访问体验。可以准确说出 NSCache 的 24 MB 成本预算和 300 项、URLCache 的 120 MB 磁盘、12 个预取和 4 路并发。现有材料没有证明它们是经过多设备 profiling 得到的最优值，因此可以说后续会用真机内存压力和命中率继续校准。

24 MB 是否代表图片实际只占 24 MB

不能这样保证。当前代码传给 NSCache 的 cost 是下载 Data 的字节数，压缩图片解码后的像素内存可能更大；NSCache 的淘汰也带有系统自主性。更严谨的改进是按解码后的像素尺寸估算成本，再用真机内存曲线校准预算。

你怎样证明任务真的被释放

现有代码证据包括 disconnect、deinit、流终止回调和 clear 中的取消路径，测试还覆盖了清理以后迟到响应不能重新写回缓存。更完整的验证会在真机重复进入和退出相关页面，再用 Memory Graph 检查对象引用路径，用 Allocations 观察曲线是否回落。

03

CPU、主线程与并发

CPU 问题要从用户现象出发。滚动掉帧、点击不响应和启动慢都可能与主线程有关，但高 CPU 与线程阻塞需要不同处理。

这一章必须会

  • 主线程负责用户事件和界面更新
  • 忙碌主线程与阻塞主线程不同
  • async 不保证自动转到后台线程
  • MainActor 隔离 UI 相关状态
  • 使用 Time Profiler 和 Hangs 找热点

Part A · CPU 问题怎样表现

忙碌主线程

主线程持续做计算、解析、布局或绘制，CPU 较高，来不及处理输入和下一帧。

阻塞主线程

主线程等待锁、同步 I/O 或其他线程。此时界面同样无响应，CPU 却可能并不高。

后台 CPU 过高

高频轮询、图像处理、解析或失控任务可能耗电和发热，即使界面暂时不卡。

SwiftUI 重复工作

状态范围过大、列表身份不稳定、body 中计算过重，会让界面反复执行不必要的工作。

Part B · async、Task 和 MainActor

异步表示可以暂停，不能直接等同于后台线程

Swift 并发运行时在任务和线程之间调度工作。异步函数暂停以后，恢复时不保证使用原来的线程。直接创建的 Task 还会继承当前 actor 隔离。如果它从 MainActor 环境创建，闭包中的同步重计算仍可能占用主线程。

await

标记可能暂停的位置。等待网络时可以释放执行线程，不代表 await 后的所有工作都在后台。

Task

创建异步工作，继承当前优先级、actor 隔离和任务局部值。需要管理取消和生命周期。

@MainActor

让 UI 状态和相关方法在主 actor 上串行访问，避免手动到处切换主队列。

actor

隔离共享可变状态，一次只允许一个任务访问 actor 隔离的代码。

@MainActor
final class FeedViewModel {
  private var loadTask: Task<Void, Never>?
  private(set) var items: [Item] = []

  func refresh() {
    loadTask?.cancel()
    loadTask = Task {
      do {
        let data = try await api.fetchFeed()
        // 网络等待不会持续占用主线程
        // 大量同步解析仍需单独评估执行位置
        items = try decoder.decode([Item].self, from: data)
      } catch is CancellationError {
        return
      } catch {
        handle(error)
      }
    }
  }

  deinit { loadTask?.cancel() }
}

示例中的解码是否需要移出 MainActor，取决于数据量和测量结果。小数据直接处理可能更简单。大数据导致主线程热点时，再把纯计算放入适合的并发域，并保证传递的数据满足并发安全要求。

Part C · SwiftUI CPU 检查点

  • 让 body 保持廉价，不在其中同步解析大 JSON、处理图片或排序大型数据。
  • 把状态放在真正需要它的最小范围，避免一个变化让大面积视图重新计算。
  • 列表使用稳定身份，不用会随刷新改变的随机 ID。
  • 搜索、滚动和传感器事件需要节流或防抖，避免每次输入都触发昂贵操作。
  • 取消离开页面后没有意义的 Task、Timer、SSE 和轮询。

async 函数会自动在后台线程执行吗

不会这样保证。async 表示函数可以暂停。任务由 Swift 并发运行时调度，Task 还可能继承当前 actor。UI 代码通常由 MainActor 隔离。

CPU 使用高一定是问题吗

不一定。短时间完成用户主动触发的重计算可能合理。持续高占用、卡顿、发热和耗电更值得处理，仍需结合用户路径和时间线判断。

高 CPU 和主线程卡住有什么区别

忙碌主线程通常持续执行代码，CPU 较高。阻塞主线程在等待锁或同步资源，CPU 可能较低。两者都会导致界面无响应，但修复方向不同。

为什么不能处理每一帧

相机帧率通常高于界面提示和自动拍摄需要的判断频率。分析速度跟不上输入速度时，旧帧会排队，占用 CPU 并增加结果延迟。PHASE 的处理方式是限制采样间隔，并保证同一时间只有一次检测，让系统始终处理较新的帧。

为什么使用 Task.detached

SkinScanViewModel 由 MainActor 管理界面状态。如果直接在继承 MainActor 的任务里做同步图像分析，可能阻塞界面。最终照片分析和准备属于不直接操作 UI 的纯计算，因此放到 detached task，完成以后再回到 MainActor。使用时仍要确保传入对象满足并发安全。

Part A · 一次 React 更新

一次更新会经过触发、计算差异、提交与绘制

01Trigger首次挂载，或者 state、props、context、外部 store 发生变化
02RenderReact 调用函数组件，递归计算新的 JSX 结果
03ReconcileRender 过程中根据类型、位置和 key 判断哪些节点能够复用
04Commit把必要变化写入 DOM 或 Taro 宿主环境
05Paint浏览器或小程序视图层完成布局、绘制和合成

React 的 Render 是执行组件函数并计算结果，不等于浏览器已经画出像素。组件可以重新 Render，但计算结果没有变化时，Commit 可能不修改对应 DOM。Commit 完成以后，浏览器才根据 DOM 与 CSS 做样式计算、布局和绘制。

useMemo复用一次计算结果过滤、排序、分组等计算成本可测，并且依赖稳定不能用来保证业务正确性，依赖每次变化就没有收益

Part C · Taro 与普通 React 网页的区别

PHASE 小程序没有直接操作浏览器真实 DOM

PHASE MiniApp 使用 React 18.3.1 和 Taro 4.0.9。React 先更新 Taro 的虚拟 DOM。Taro 运行时把变化整理成小程序可传输的数据，通过 setData 从逻辑层送到视图层，再由微信小程序模板渲染。普通 React 网页的 Commit 目标是浏览器 DOM；Taro 小程序的 Commit 还要经过运行时适配和 setData。

因此小程序性能需要额外关注更新次数、序列化数据量、页面结构深度和逻辑层到视图层的通信。网页中的 DOM 节点数和 Layout 成本仍然重要，但不能把 Chrome DOM 更新路径原样套到微信小程序。

结合项目的九十秒回答

React 更新可以分成触发、Render 和 Commit。state 或外部 store 变化以后，React 会调用相关组件，计算下一份 JSX，再把必要变化提交到宿主环境。浏览器网页会修改 DOM，PHASE 小程序通过 Taro 把虚拟 DOM 变化转成 setData，再交给微信视图层。性能上我会先用 Profiler 找出更新频率高或单次耗时长的组件。PHASE 聊天使用 useSyncExternalStore，并缓存稳定快照；首页对排序和日期分组使用 useMemo，操作函数使用 useCallback，列表使用稳定 event id。数据加载还做了 SWR、请求去重和预取。当前小程序每个 SSE text_delta 都会发布状态，我会重点测量这条路径的 Render 次数和 setData 数据量。如果确认它造成卡顿，再像 iOS 端一样合并高频文本更新，并用同一段回复和同一台低端设备比较修改前后。

继续追问

Virtual DOM 是什么

它是用 JavaScript 对象表达的界面结构。React 根据新的组件输出和上一次结果判断宿主环境需要哪些更新。Virtual DOM 仍然需要计算，也不能保证任何页面都快。组件树规模、更新频率和真实 DOM 或 setData 成本仍需测量。

React 为什么需要 key

key 给同一父节点下的列表项提供稳定身份。插入、删除和排序以后，React 可以把新旧条目对应起来，保留应该保留的组件状态，并减少错误复用。PHASE 的 Journal 列表使用事件 id，适合这种会追加和删除消息的场景。

useMemo 和 useCallback 有什么区别

useMemo 缓存计算结果，useCallback 缓存函数本身的引用。两者都根据依赖是否变化决定复用。它们带有比较和维护成本，需要针对重复且昂贵的工作使用。

为什么 useCallback 不一定提高性能

创建普通函数通常很便宜。子组件没有使用 memo，或者函数没有进入依赖比较时，稳定引用可能没有实际收益。依赖经常变化时，函数还是会重新创建。应当用 Profiler 看它是否减少了昂贵子树的 Render。

怎样判断 React 页面为什么卡

先复现具体交互，再用 React DevTools Profiler 看哪些组件提交、每次耗时和触发原因，同时用浏览器 Performance 查看 JavaScript 长任务、Layout 与 Paint。小程序还要检查 Taro setData 次数和数据量。随后只处理成本最高的路径。

为什么不能给每个组件都加 memo

memo 会增加 props 比较与代码复杂度。只要一个对象或函数 prop 每次都是新引用，缓存就容易失效。组件本来很轻时，比较成本也可能接近重新 Render 的成本。

PHASE 的流式消息还可以怎样优化

先记录一次长回复产生多少 text_delta、多少 React Commit 和多少 setData。若更新过密，可以先在内存中累积文本，使用 requestAnimationFrame 或固定的短间隔统一发布；同时把流式气泡与静态历史列表拆开，避免整段历史跟随每个 token 更新。

PHASE 一次聊天的完整 SSE 流程

这道题要从用户点击发送开始，一直讲到 Agent 选择工具、模型流式输出、服务端持久化和 iOS 把最终消息加入列表。核心聊天和服务端主动事件使用两条不同的 SSE 连接。

先记住两条连接

  • POST /api/chat 是一次聊天请求对应的一条 SSE 响应
  • GET /api/events 是服务端主动事件流
  • SSE 是服务端向客户端单向推送
  • 发送消息仍然通过 HTTP POST 请求体
  • 同一次回复可能包含多个 LLM 和工具轮次
  • turn_end 表示当前回复结束

端到端主链路

从点击发送到最终气泡共有十二步

  1. 客户端先做乐观更新

    ChatViewModel.sendMessage 立即创建 user message 和 clientTurnId，追加到 messages，并把界面设为 submitted 与 thinking。

  2. 构造聊天请求

    ChatSSEClient 获取有效 access token，向 /api/chat 发送 JSON。请求包含 text、images、episode_id 与 client_turn_id，并声明接受 text/event-stream。

  3. 服务端鉴权和校验

    认证中间件提供 userId、Supabase 客户端和 Main session。路由解析 JSON、校验 text，并在指定 episode 时查询归属，避免访问其他用户会话。

  4. 立即打开 SSE 响应

    服务端关闭缓存与代理缓冲，先发送 turn_start 和 submitted 状态。主会话查询和上下文准备不会挡住用户看到已提交状态。

  5. 确定会话并保存用户消息

    服务端得到 Main 或 episode session id，把 user message 写入 journal_events。这一写入异步启动，失败会记录日志并重试一次。

  6. 取得或创建 Agent

    Agent Registry 按 session id 复用内存中的 Agent。没有实例时创建 Agent，加载该用户与该 episode 的历史消息，并注入会话上下文。空闲 Agent 会在 30 分钟后清理。

  7. 组装上下文与能力

    Agent 配置系统提示、用户上下文、最近完整对话、模型和工具。工具包括用户资料、皮肤历史、库存、routine、watchlist、商品检索与 memory。

  8. 进入 Agent loop

    agent.prompt 调用模型并产生 kernel events。需要工具时，模型先输出 tool call，服务端执行工具，把 tool result 放回上下文，再开始下一轮模型调用。

  9. 转换成 SSE 协议

    服务端把 kernel events 映射为 llm_start、tool_start、tool_end、text_delta、message_end 与 turn_end。写队列保证帧按顺序发送。

  10. iOS 逐帧解析

    URLSession.bytes 逐行读取响应，SSEParser 按空行切出事件帧，JSONDecoder 再把 data 解析成 ServerMessage，交给 AsyncThrowingStream。

  11. 更新流式界面

    ViewModel 在 MainActor 处理事件。text_delta 追加到 currentMsg，界面文本最多约 50ms 发布一次；工具和 LLM 事件更新步骤状态。

  12. 完成与持久化

    message_end 给出权威全文，turn_end 触发服务端保存 assistant message。iOS 把最终文本、工具信息和步骤组成 assistant message，追加到 messages，随后清理 thinking 与 streaming 状态。

两条 SSE 不要混淆

聊天回复随 POST 返回，主动事件走单独 GET

  • ChatSSEClient 每次发送都建立 POST /api/chat。请求体把用户输入送到服务端，同一个 HTTP 响应持续返回该 turn 的 SSE 帧。
  • UserEventsSSEClient 建立 GET /api/events 长连接，处理 vision result、upload complete 等服务端主动事件。它的 isConnected 只表示这条事件流状态。
  • 小程序当前没有独立的共享事件流。它也为每次聊天打开一条 chunked POST，并在 drainChatStream 中消费事件。
  • 用户点击停止时，客户端先取消本地流，再调用 POST /api/chat/abort。服务端找到对应 session 的 pending turn 和 Agent，并传播 abort。

性能与可靠性细节

帧顺序

服务端用 Promise write queue 串行写 SSE，避免同步订阅回调让帧交错或响应提前关闭。

UI 节流

iOS 累积每个 text_delta，但大约每 50ms 才更新一次 streamingText，降低 SwiftUI 高频刷新。

会话隔离

clientTurnId 与 episodeId 把回复绑定到发起它的 turn 和会话，切换会话后旧流不能覆盖新状态。

中断处理

AsyncThrowingStream 终止时取消 Task。网络失败会清理活动状态并给用户可操作的错误。

持久化

用户与 assistant 消息写入 journal_events，Agent 首次创建时按 userId 和 episodeId 加载历史。

工具循环

模型调用可以输出工具请求。工具结果加入上下文以后，Agent 再发起模型调用，直到得到最终回答。

结合项目的两分钟回答

PHASE 的聊天使用一次 POST 加一条 SSE 响应。用户在 iOS 点击发送以后，ChatViewModel 先把用户消息加入本地列表，生成 clientTurnId，并显示 submitted。ChatSSEClient 带 Bearer token，把 text、可选图片、episodeId 和 clientTurnId POST 到 /api/chat。服务端校验用户和 episode 归属，马上打开 SSE，先发 turn_start 和状态事件，然后确定 session，把用户消息写入 journal_events，并按 session 取得或创建 Agent。新 Agent 会加载这个用户的历史，配置系统提示、用户上下文、模型和工具。agent.prompt 进入循环，模型可能先调用商品、皮肤历史或 routine 等工具，工具结果再回到上下文，继续下一轮模型调用。服务端把 kernel events 转成 tool_start、llm_start、text_delta、message_end 和 turn_end，并通过写队列保持顺序。iOS 用 URLSession.bytes 逐行读取，SSEParser 切帧，JSONDecoder 转成 ServerMessage。text_delta 会累积，但界面最多约 50ms 更新一次。message_end 给出完整内容，turn_end 后客户端生成最终 assistant message 并清理流式状态，服务端也把 assistant message 保存到 journal_events。另有一条 GET /api/events 负责服务端主动事件，它不承担这次聊天回复。

继续追问

为什么 SSE 请求使用 POST

原生 EventSource 主要用于 GET。PHASE 需要把用户文本、图片和 episodeId 放进请求体，因此使用普通 HTTP POST，再让响应保持 text/event-stream。iOS 用 URLSession.bytes，小程序用 chunked Taro.request 消费响应。

SSE 和 WebSocket 在这里怎样选择

聊天数据方向很清楚。用户输入通过一次 POST 上行，服务端回答持续下行。SSE 基于 HTTP，重连、代理和抓包相对直观。若双方都需要长期高频主动发送、实时协作或二进制交互，WebSocket 更合适。

为什么 message_end 和 turn_end 都需要

message_end 表示一条 assistant message 的内容已经完整，可以提供权威全文。turn_end 表示整个 Agent turn 完成，其中可能包含多轮模型调用和工具执行。工具调用产生的中间 assistant message 不能提前结束整个 turn。

模型调用工具以后发生什么

Agent loop 识别 assistant message 中的 toolCall，按名字找到工具并执行。当前 kernel 的统一参数校验仍是透传，具体类型、长度和业务约束主要由各个 PhaseTool 自己检查。工具结果包装成 toolResult message，加入上下文，再调用模型。模型读取工具结果以后生成下一步调用或最终文本。

为什么 text_delta 不直接每次刷新界面

模型可能很快地产生许多小片段。每个片段都修改可观察状态，会增加主线程状态发布、View 重新计算与布局次数。iOS 保留完整文本，但把对 UI 的发布合并到约 50ms 一次，用户仍然感到连续输出。

客户端中途断网会怎样

URLSession 流抛出错误，AsyncThrowingStream 结束。ViewModel 清理当前 turn，并加入连接中断提示。旧版历史模式还会在成功结束后按 2、4、8 秒回查历史，避免已经持久化的 assistant reply 没有进入本地列表。

服务端如何避免不同用户会话串线

路由从认证上下文取得 userId。指定 episode 时同时按 episode id 和 user id 查询归属。Agent Registry 也记录 userId，加载历史时按 user_id 和 episode_id 双重过滤。

07

从一次网页请求到用户看到页面

这道题需要分清首次打开页面和页面内发起 API 请求。HTML 提供结构，CSS 参与样式和布局，JavaScript 执行业务逻辑，React 负责从状态计算界面，浏览器最终生成像素。

这一章必须会

  • 网络建立连接并取得 HTML
  • HTML 解析产生 DOM
  • CSS 解析产生 CSSOM
  • JavaScript 可能影响解析与 DOM
  • React Render 与浏览器 Paint 是不同阶段
  • Render tree 经过 Layout、Paint 与 Composite

场景 A · 首次打开 React 网页

浏览器从 URL 走到第一帧像素

  1. 解析 URL 与检查缓存

    浏览器确定协议、主机、端口和路径，并检查 HTTP 缓存或 Service Worker 是否已有可用响应。

  2. 建立网络连接

    需要联网时先解析 DNS，再建立 TCP；HTTPS 还要完成 TLS。随后发送 HTTP 请求并等待响应头和内容。

  3. 解析 HTML

    收到字节后解码成字符和 token，逐步建立 DOM。解析器发现 link、script、img 等资源时会继续发起请求。

  4. 构建 CSSOM

    CSS 文件与 style 内容被解析成 CSSOM。浏览器需要样式规则来确定可见节点的计算样式，CSS 通常会影响首次绘制时机。

  5. 下载并执行 JavaScript

    普通 script 可能暂停 HTML 解析，等待脚本下载和执行。defer 会在 HTML 解析后按顺序执行，async 下载完成后尽快执行。

  6. React 首次 Render

    JavaScript bundle 执行 createRoot 和 render。React 调用组件，把 props 与 state 计算成 JSX 对应的元素树。

  7. React Commit

    React 创建或更新真实 DOM 节点，绑定必要的属性和事件，使 DOM 与组件输出一致。

  8. 浏览器生成像素

    DOM 与 CSSOM组合成可见的 Render tree。浏览器计算 Layout，生成绘制指令并 Paint，最后把不同图层 Composite 到屏幕。

HTML、CSS、JavaScript、React 各自负责什么

部分主要责任对性能的典型影响
HTML文档结构、语义和初始资源引用，解析后形成 DOM文档体积、节点数量、资源发现顺序
CSS选择器、计算样式、尺寸与布局约束，解析后形成 CSSOM阻塞首次绘制、复杂样式计算、Layout 与 Paint
JavaScript事件、数据请求、状态变化和 DOM 或框架逻辑下载与解析成本、主线程长任务、解析阻塞
React根据 props、state 与 context 计算组件树，并提交必要宿主更新组件 Render 范围、重复计算、提交次数
浏览器渲染引擎样式计算、Layout、Paint 与 Composite大范围布局、昂贵绘制、过多图层与掉帧

场景 B · 页面内点击后请求 API

已有页面不会重新下载整份 HTML

01事件回调浏览器事件循环执行点击处理函数
02Loading 状态setState 触发 React Render 与 Commit
03Fetch网络层发送 API 请求，主线程可以继续处理其他任务
04响应处理Promise 回调解析 JSON 并更新 state

API 请求返回以后，JavaScript 通常只更新一部分 state。React 重新计算受影响组件，Commit 必要 DOM 变化，浏览器再对相关区域做样式、布局或绘制。是否触发 Layout 取决于改动的属性；只改变 transform 或 opacity 时更容易交给合成阶段处理。

容易混淆的三个 Render

  • React Render　调用组件并计算下一份界面描述。它是 JavaScript 计算。
  • React Commit　把差异写到真实 DOM 或 Taro 宿主。它可能产生 DOM mutation 或 setData。
  • Browser Rendering　浏览器根据 DOM 与 CSS 做 Style、Layout、Paint 和 Composite，最终形成屏幕像素。

面试可直接复述的两分钟回答

用户首次打开 React 网页时，浏览器先解析 URL，检查缓存，然后经过 DNS、TCP 和 HTTPS 的 TLS 建立连接，发送 HTTP 请求。收到 HTML 后，解析器逐步构建 DOM，并发现 CSS、JavaScript 和图片等资源。CSS 被解析为 CSSOM；普通同步脚本可能暂停 HTML 解析，defer 脚本会等 HTML 解析完成。React bundle 执行后，createRoot 触发首次 Render，React 调用组件计算 JSX，再在 Commit 阶段创建或更新真实 DOM。浏览器把 DOM 和 CSSOM组合成 Render tree，完成样式计算、Layout、Paint 和 Composite，用户才看到像素。页面已经打开以后，用户点击按钮发起 API 请求时，事件处理函数可以先 setState 显示 loading，再用 fetch 请求数据。响应回来后 Promise 回调解析数据并再次 setState，React 重新 Render 和 Commit变化部分，浏览器再绘制受影响区域。React Render、React Commit 和浏览器 Paint 是三个不同阶段。
回答顺序 · 网络 → DOM 与 CSSOM → JavaScript → React → Layout、Paint、Composite

继续追问

CSS 为什么会影响首次渲染

浏览器需要 CSSOM 才能确定节点的计算样式并构建 Render tree。缺少关键样式时直接绘制容易产生无样式内容和大幅跳动，因此外部 CSS 通常会阻塞首次绘制。

JavaScript 为什么可能阻塞 HTML 解析

同步脚本可能读取或修改当前 DOM，浏览器需要保证执行顺序，所以解析器遇到普通 script 时可能暂停，等待脚本下载和执行。defer 与 async 改变下载和执行时机，但两者的顺序保证不同。

DOM 和 Render tree 有什么区别

DOM 表示文档节点和语义，包含 head 等不直接显示的内容。Render tree 只保留参与视觉呈现的节点，并带有计算后的样式。display: none 的节点通常不会进入 Render tree。

Layout、Paint、Composite 分别做什么

Layout 计算元素尺寸与位置。Paint 生成文字、颜色、边框和阴影等绘制指令。Composite 把已经绘制的图层按顺序组合到屏幕。改变宽高常会触发 Layout，改变颜色会触发 Paint，transform 与 opacity 常可只影响 Composite。

React 重新 Render 会重建整个 DOM 吗

通常不会。React 可以调用一段组件树重新计算，但 Commit 只应用与上一次结果不同的必要宿主变化。组件类型、位置和稳定 key 帮助它复用已有节点与状态。

JSX 是 HTML 吗

JSX 是 JavaScript 的语法扩展，用来描述元素结构。构建工具会把 JSX 转换成 JavaScript 调用或编译结果。React 根据这些元素描述进行 Render，最终才在网页端创建 DOM。

怎样分析首屏慢

先用 Network 看 DNS、连接、TTFB、资源体积和请求瀑布，再用 Performance 看脚本长任务、样式计算、Layout 与 Paint。React Profiler用于确认组件 Render 与 Commit 成本。指标要分开记录服务器等待、资源加载和主线程渲染。

PHASE Agent Harness、准确率与工具可靠性

这里的 Harness 是围绕模型的一整套运行环境。它负责提示词、上下文、工具注册、循环执行、错误边界、事件流、持久化和评测。iOS 与小程序共享同一套后端 Harness，客户端负责发请求、消费 SSE 和呈现结果。

先记住六句话

  • 模型本身不会直接访问数据库
  • 服务端把工具名称、说明和参数 Schema 发给模型
  • 模型只生成 tool call，kernel 才执行真实函数
  • 工具结果进入上下文，模型再决定下一步
  • 准确率要按意图、工具、参数、grounding 和任务结果拆开
  • 当前代码有真实防线，也有统一参数校验和错误语义的缺口

先把边界讲清楚

客户端没有各自运行一套 Agent

iOS 的 ChatSSEClient 与小程序的 openChatStream 都向后端 POST /api/chat。Agent factory、kernel loop 和 11 个 PhaseTool 都在 PHASE backend。两个客户端共享推理、工具和持久化逻辑，只在网络适配和界面状态更新上不同。

因此“iOS Agent Harness”和“小程序 Agent Harness”更准确的说法是同一个服务端 Harness，外接两个客户端适配层。这样能避免重复实现工具权限、上下文和错误恢复。

Harness 架构

一次回答经过五个责任层

模型怎样使用工具

模型负责选择，代码负责执行

  1. 注册能力

    agent-factory.ts 汇总 11 个工具，每个工具包含 name、description、parameters 和 execute。

  2. 绑定身份与数据源

    factory 把认证后的 userId、Supabase client 和语言市场信息绑定进 ToolContext。模型不能自行指定另一个 userId。

  3. 发送工具定义

    kernel 构造模型请求时，把 system prompt、消息和工具 Schema 一起交给 provider。模型只看到能力描述，并没有数据库连接。

  4. 决定首轮策略

    通常由模型自动选择。推荐和皮肤分析等高风险 grounding 场景会经过 intent gate，必要时把首轮 tool choice 固定为指定函数。

  5. 生成 tool call

    模型返回工具名、toolCallId 和 JSON arguments。OpenAI 兼容 provider 即使把 finish reason 写成 stop，只要带 tool calls，适配层也会规范化为 toolUse。

  6. 执行真实函数

    kernel 按名字查找 AgentTool，调用 execute。PhaseTool 再查询 Supabase、商品目录或写入用户状态。

  7. 回填结果

    结果被包装成 toolResult message，和原 toolCallId 配对，加入同一个上下文。

  8. 继续推理

    模型读取真实结果后，可以调用下一个工具，也可以生成最终文本和结构化卡片。没有更多 tool call 时 turn 才结束。

准确率该怎样回答

仓库没有一个可代表所有回答的总准确率

“Agent 准确率”至少包含五件不同的事。一个百分比无法同时说明意图判断、工具选择、参数正确、数据 grounding 和最终建议是否有用。当前仓库能给出部分真实指标，但不能把它们包装成整体回答准确率。

历史回答诱发了零工具调用的自我复制

system prompt 明确规定历史商品不能作为本轮 grounding。单靠静态规则时，记录历史上的目录调用率只有 2/5。

在当前用户消息前插入短的 REGROUND_REMINDER。Harness 中目录调用率恢复到 5/5，但一条已经被旧回答污染的 live history 仍能突破提醒。

当前代码缺口

这部分适合在追问中主动承认

  • 统一 Schema 校验尚未落地　phase-ai 的 validateToolArguments 当前直接返回原 arguments。部分 PhaseTool 使用 validateArgs 检查类型和长度，覆盖并不完全一致。

最小权限上下文

ToolContext 由服务端绑定认证 userId 和 Supabase client。update_state 会忽略模型传来的 user_id，并重新写入上下文 userId。

确定性首轮 gate

高风险 intent 不完全依赖模型自由选择。常见推荐语句走 regex 快路，其他表达走温度为 0 的分类器。

继续追问

你们 Agent 的准确率是多少

先说明没有一个覆盖最终回答的总准确率。随后给可核验的子指标。CN intent classifier 在 44 条平衡 gold set 上 macro recall 0.932，两个强制工具类的 recall 都是 1.0，forced precision 是 1.0。商品 grounding 另用工具调用率、目录解析率和目录外品牌检查。最后补充仍缺生产任务成功率和医疗建议正确性的统一评估。

为什么不能直接回答 93.2%

0.932 测的是 11 类意图的 macro recall。它不验证工具参数、数据库写入、商品建议理由和用户最终是否解决问题。把分类指标当成整体准确率会混淆分母，也会夸大系统能力。

模型怎样知道有哪些工具

服务端在模型请求的 tools 字段里提供每个工具的 name、description 和 parameters Schema。system prompt 说明什么场景使用什么工具。模型输出结构化 tool call，kernel 才执行对应函数。模型不会获得 Supabase client 或直接运行 TypeScript。

是谁决定调用哪个工具

大多数轮次由模型按 prompt 和工具描述自动选择。推荐与皮肤分析的首轮增加确定性 intent gate。常见推荐表达走 regex 快路，其他表达走分类器。gate 只固定首轮，工具结果回来后的轮次恢复 auto。

工具调用失败会不会让整个回答失败

如果 execute 抛异常，kernel 会转成 isError toolResult，再进行下一轮模型调用，所以单个工具异常通常不会直接结束 turn。若模型 provider 本身最终失败，服务端会发送 error 与 turn_end。还要说明不少 PhaseTool 自己返回 JSON error，这类错误目前不会统一变成 isError。

工具参数是怎样校验的

模型侧有 JSON Schema。部分 PhaseTool 在 execute 内调用 validateArgs，检查 required、类型、长度和数组数量，写操作还有 enum、用户归属和 active catalog 约束。当前 kernel 的 validateToolArguments 仍是透传，所以不能声称已经有完整统一的 runtime Schema validation。

怎样防止 Agent 修改别人的数据

userId 来自认证上下文并绑定进 ToolContext。工具查询按用户过滤。update_state 会删除模型参数里的 user_id，再写入上下文 userId。episode 查询也同时按 episode id 与 user id 校验。安全边界放在代码与数据库查询上，不能只依赖 prompt。

为什么工具不全部并行执行

当前 kernel 顺序执行多个 tool call。写工具可能依赖前一步结果，重复或乱序会带来副作用。顺序执行也便于每一步后检查用户 steering 并跳过剩余调用。以后可以只并行互不依赖、只读且幂等的工具，前提是先给工具补 effect metadata。

怎样降低幻觉和商品错误

本轮必须调用目录工具，历史推荐不能直接复用。intent gate 强制高风险首轮工具。最终商品卡使用工具结果与 active catalog 重新生成品牌、图片、价格和链接。无法解析的商品和整个空卡都会被丢弃。

怎样处理模型供应商失败

stream wrapper 在文本、thinking 或 tool call 开始前保留重试安全边界。只有 rate limit、server、timeout 和 connection 等可重试 provider failure 才尝试一次 fallback。开始输出后不重试，避免重复文本或工具副作用。切到 fallback 后，本次 run 的后续轮次继续使用它。

你做了哪些性能优化

优先讲本人提交。你把上下文限制到最近消息，并从完整 user turn 开始，降低 token 又不破坏 toolCall 与 toolResult 配对。你还把 SSE 的 turn_start 提前到 Main session 和 Agent 准备之前，减少静默等待。iOS 客户端把流式状态发布限制到约 50ms 一次。团队当前还用了 Agent 复用、并行上下文查询、intent regex 快路和 post-turn suggestions。

如果工具已经成功，最终卡片为什么还会消失

成功调用只证明拿到结果。模型输出的 recommendation_card 还必须是可解析 JSON，引用也必须能映射到 active catalog。任一步失败都会 fail closed。这样宁可少一张卡，也不把未验证商品展示给用户。

framework 通常指可复用的 Agent 类、loop 和 tool interface。Harness 范围更大，还包含特定产品的 prompt、上下文注入、会话、工具集合、provider fallback、SSE、持久化、grounding、观测和 eval。PHASE kernel 更接近 framework，phase-agent、phase-tools 与 phase-server 合起来形成产品 Harness。

可以主张　问题定义、约束选择、代码审查、测试验收、发现问题后的迭代，以及现在能够解释的具体机制。

需要限定　Agent 生成过多少实现、哪些方案来自现有代码、当时有没有使用 Instruments，以及是否存在可复现的性能数据。

面试官追问那你的技术贡献到底是什么

先选一个有提交和测试依据的例子。比如图片加载优化中，你可以讲清重复 URL 请求合并、预取并发限制、缓存容量与清理机制，再说明自己如何验证相同请求只发一次、清理后旧请求不会重新写回缓存。贡献要落到决策、审查与验证，不要只说自己会使用 AI。

面试官追问离开 Agent 你还能完成吗

可以回答自己完成需求的速度会下降，也需要查文档，但现在能够独立读懂这些代码、解释关键生命周期并设计验证。随后现场推导一个小问题，让面试官看到你的理解。不要承诺可以不查资料复写整个项目。

完全不知道时的回答模板

“这个机制我没有系统掌握，所以准确实现我不想猜。我目前知道它与某个运行过程有关。我会先区分用户看到的现象，再用对应工具确认热点。如果在我做过的项目里，我会先从这些位置检查。完成测量以后再决定是否修改。”

这段回答不能代替知识。它的作用是保留诚实边界，同时让面试官看到你仍能继续分析。
